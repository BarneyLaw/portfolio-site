I understand what CS2103T is trying to impart. Software engineering is not the act of sitting alone, entering a flow state and producing a perfect application by midnight. Real software has existing code, requirements, tests, documentation, deadlines and other people. Someone must coordinate all of that.

The module teaches those realities. Unfortunately, the way it taught them in my semester felt restrictive, overworked and deeply underwhelming. It gave software engineering the atmosphere of corporate *saikang*: plenty of process, plenty of artefacts, and not nearly enough joy in building the thing itself.

## Content overview

CS2103T covers the practices surrounding medium-sized software projects. Version control is a major part of the experience: commits, branches, pull requests, merges and conflict resolution become team tools rather than Git commands memorised for an individual assignment. The project also demands planning, issue tracking, incremental delivery and coordination between developers working on the same codebase.

The technical material includes requirements, software architecture, object-oriented design, code quality, testing and debugging. Unit and integration tests help protect existing behaviour while the system changes. Documentation matters because another developer should be able to understand and continue the project. UML diagrams are used to describe structure and interactions without reading every line of code.

The team project is deliberately a brownfield exercise. Instead of creating any product with any stack, teams extend an existing Java application descended from AddressBook-Level3. The application is built around typed commands and a desktop interface, and the module imposes constraints on how far it can be transformed. Coding itself is largely treated as prior knowledge; the focus is the process and quality of contributing changes to an existing system.

That premise is legitimate. Most professional engineers join codebases they did not invent. The skill of reading, extending and not breaking an existing system is arguably more representative of ordinary work than starting a clean repository every month.

## The content is real

The strongest parts of CS2103T are the ones that survive outside the module. Git is indispensable when several people modify the same project. Small, reviewable commits make mistakes easier to locate. Pull requests create a place to discuss design and quality. Automated tests make refactoring less terrifying. Planning forces a team to decide what “done” means before the deadline arrives.

Teamwork is also a real engineering skill, although it is difficult to teach cleanly. Interfaces between people can fail just as badly as interfaces between components. If ownership is unclear, work is duplicated or ignored. If a branch lives too long, integration becomes painful. If one member silently redesigns a shared component, everyone else discovers the new architecture through merge conflicts.

These lessons are valuable because they are inconvenient. A solo project can hide poor communication and process; a team project exposes them immediately.

## The project drains the fun out of it

My problem is the experience built around those lessons. The workload was ridiculous, but the project still felt restrictive and underwhelming. The prescribed stack and CLI-first direction limited what teams could build, while the volume of required artefacts made minor changes feel surrounded by paperwork.

I understand the logistics. A large cohort needs a common baseline, predictable scope and comparable assessment. Allowing every team to choose a language, framework and product would make support and grading much harder. Constraints also prevent ambitious teams from accidentally turning one module into a failed startup.

Even so, there should be a better balance. A software-engineering course ought to demonstrate how process helps people build something worthwhile. Here, the process often seemed to be the product. The assignments were boring, and the restrictions made it difficult to feel ownership of the application. If the intended lesson is that real-world software work is mostly toil imposed by someone else's system, then the simulation was almost too successful.

UML added to that feeling. Diagrams can be useful when they clarify a complicated relationship or interaction, and software teams still use visual models in various forms. But manually maintaining detailed diagrams for assessment can quickly become documentation theatre. The diagram exists because a rubric expects it, not because the team needed it to think.

## Verdict

CS2103T is mixed. Its subject matter—version control, collaboration, design, testing, planning and maintenance—is essential. I believe the module's premise has real potential, and I understand why it uses a constrained brownfield project.

The implementation needs a rethink. Less busywork, more freedom where logistics permit, and a project that lets students care about the result would make the same lessons much more convincing. Software engineering is full of necessary discipline, but discipline should enable creation. It should not make creation feel incidental.

*This review reflects my run of the module. Project constraints and teaching arrangements can change between semesters.*
