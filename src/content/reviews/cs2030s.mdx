CS2030S was the point where programming started to materialise into real-world objects—literally.

CS1101S taught me to see computation through functions, abstraction and evaluation. CS2030S took the next step and asked how a larger program can represent a world full of things with identities, behaviours and relationships. Understanding object-oriented programming felt like unlocking a DLC for programming: the map had not changed, but suddenly many structures that were previously invisible became obvious.

I recommend the module, with a special shoutout to the TA who continued giving consultations during exam week. In a course where one type error can produce a paragraph of Java diagnostics, that support mattered.

## Content overview

The course uses Java to teach modelling, abstraction and disciplined program design. Classes and objects form the starting language: a class describes a kind of entity, while an object represents a particular instance with state and behaviour. Encapsulation asks us to hide internal details behind a stable interface. Inheritance and polymorphism then let different objects participate in a common abstraction while supplying their own behaviour.

This is where examples begin to resemble software you can imagine building. A game might contain players, enemies, items and abilities. They share common contracts, but each responds differently when updated or used. Once that clicks, OOP stops looking like ceremony around variables and becomes a way to organise a changing world.

The module also spends substantial time on Java's type system, generics and functional ideas. Functions can be supplied as behaviour, values can be transformed through pipelines, and lazy computation can delay work until it is needed. The broad goal is not merely to memorise Java syntax. It is to express a design so that invalid combinations become difficult—or ideally impossible—to represent.

## Functional programming, except it is Java

The functional-programming portion was another round of insanity. Functional ideas themselves are elegant: avoid unnecessary mutation, compose small transformations, and make data flow easier to reason about. Teaching those ideas through Java, however, can feel like watching a language wear an outfit tailored for someone else.

Java supports lambdas, generic functional interfaces and streams, but the result often looks like patchwork. Type signatures expand, wrapper types appear, and a simple idea can acquire enough punctuation to become an archaeological site. Is this the clearest way to learn functional programming? I am still not convinced.

Yet the awkwardness is educational in its own way. It separates a programming paradigm from any single language. Functional programming is not “the syntax used by a functional language”; it is a way of structuring computation. If the ideas survive contact with Java, they are probably real ideas.

## Java is an odd place

Much of CS2030S leaves you scratching your head, and part of that is simply Java. The language is explicit, heavily typed and full of historical decisions. That strictness can be frustrating, but it also forces design questions into the open. What is the actual type of this value? Which component owns this state? Should callers depend on a concrete class or an interface? When can this operation fail?

Those questions are useful. The compiler becomes an unusually pedantic collaborator that rejects a large class of bad designs before they run. It may communicate its objections through an error message assembled by committee, but it is often pointing at something worth fixing.

The practical examinations were the most stressful part for me. Under time pressure, a small misunderstanding in a generic type or class hierarchy can spread across the entire solution. Unlike a written question, the program keeps reminding you that it does not compile. Tilting is a fair description.

The written assessments felt much fairer. They rewarded understanding of how objects interact, how types constrain behaviour and why a design is safe, rather than relying mainly on surprise.

## Verdict

CS2030S is where programming begins to feel like the construction of software rather than the solution of isolated exercises. OOP provides a practical mental model for representing systems, while the functional and type-driven portions broaden the set of tools available for controlling complexity.

Java makes parts of the journey stranger than necessary, and the practical exams can be brutal. Still, the module changed the way I imagine programs. Once objects, interfaces and polymorphism click, a large codebase becomes less like a pile of instructions and more like a collection of components with defined responsibilities.

That is absolutely worth learning.
